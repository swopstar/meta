# ADR-0001: Rust for Backends and Native Clients

**Status:** accepted
**Date:** 2026-10-17
**Supersedes:** the backend section of [ADR-0000](0000-stack.md)

## Context

[ADR-0000](0000-stack.md) chose Go for the backend and ruled out Rust for its slower iteration and steeper learning curve. Three things have changed since:

- **Development is moving to an agentic workflow.** Agents implement changes, other agents review them, and the maintainer reviews and merges every change. Where the compiler can rule out a class of bug, reviewers don't have to look for it.
- **The maintainer is now confident in Rust,** having written it by hand. That makes reviewing generated Rust code reliable rather than a bottleneck.
- **The roadmaps now include native clients.** swoptape plans mobile and desktop apps with offline playback and device sync. swopcart plans a client service (a background daemon for downloads and save sync), a client CLI and a client UI. In Go, server and client code can only be shared awkwardly.

The target hardware is unchanged: an entry-level NAS with a low-power ARM64 CPU and 1 GB of RAM.

## Decision

Use [**Rust**](https://rust-lang.org/) for backends and for shared native client code, with:

- Async runtime and HTTP: [tokio](https://tokio.rs/) and [axum](https://github.com/tokio-rs/axum)
- Database: [PostgreSQL](https://www.postgresql.org/), as before, through [sqlx](https://github.com/launchbadge/sqlx) with compile-time checked queries
- Logging: [tracing](https://github.com/tokio-rs/tracing), with structured fields

Reasons:

- **Fewer defects reach review.** The type system, ownership and exhaustive `match` rule out data races, null dereferences and unhandled errors at compile time. This makes reviewed, generated code more trustworthy. It does not catch logic errors.
- **Less memory.** With no garbage collector, memory is freed as soon as it is no longer used, rather than the heap growing ahead of collection. Async tasks compile to state machines sized to what they hold, rather than goroutines that each need their own stack. Both matter on a 1 GB machine shared with PostgreSQL.
- **One language for server and clients.** Client logic (API access, sync, offline storage) can live in a Rust crate shared by every platform: through [UniFFI](https://github.com/mozilla/uniffi-rs) bindings for native mobile apps, and directly in [Tauri](https://tauri.app/) desktop apps. For swopcart, the backend, the client service and the client UI can all be written in Rust, sharing types and API code end to end.

The frontend stack in ADR-0000 (TypeScript, React, Vite) and the single-binary, Docker Compose, reverse-proxy deployment model are unchanged.

## Alternatives considered

- **Stay with Go.** No migration cost and faster compiles. Ruled out because more classes of bug reach review, the garbage collector needs memory headroom, and native clients could not share code cleanly (gomobile is limited and poorly maintained).
- **Go for the server, a separate language for client logic.** Keeps the server stable, but implements the API client and sync logic twice and lets them drift.

## Consequences

- swoptape moves first, on a long-lived branch (see swoptape's ADR-T001). swopcart follows once the approach is proven, and its planned client service, CLI and UI are built in Rust from the start.
- **gokit is retired.** A new shared Rust library replaces it once swoptape is established. Until then, shared code is not extracted early.
- **Compile times are longer than Go's.** This slows agents' edit, build and test loop and lengthens CI. Dependency caching in CI and a lean dependency tree matter more.
- **Blocking work must stay off async worker threads.** tokio only switches tasks at `.await` points, unlike Go's preemptive scheduler. CPU-bound or blocking calls (tag parsing, filesystem walks, password hashing) go through `spawn_blocking` or a dedicated pool.
- **Static musl builds need a different allocator.** musl's built-in allocator is slow under multi-threaded load, so release builds use mimalloc or jemalloc.
- The single-binary embedding of frontend assets, previously done with `go:embed`, is done by embedding the files into the Rust binary at compile time.
